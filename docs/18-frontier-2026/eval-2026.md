# 评估 2026：基准代际

{% hint style="info" %}
**一句话**：2026 的 Agent 榜单主流已从「短任务正确率」转向 **长时程终端 / 桌面 / 科研工作流**，并强制披露 harness、effort 与防护是否干预。
{% endhint %}

*《图：这张代际图与第 10 章共用，本章只取最右两列：2026 H1 之后榜单已换成长时程任务，partial 与 strict 不可混比》*
## 先看结论

- **Terminal-Bench 4.0**：终端复杂任务（软件工程、系统配置、数据分析）的当前硬通货；Astra 57.9%、Fable 5.1 55.8% 为厂商公布量级
- **OSWorld 2.0**：真实桌面 GUI；必须区分 partial / strict 记分
- **SWE-bench 系**：Verified 仍是仓库修复标配；更难的 Pro / DeepSWE 等用于拉开前沿差距
- **τ-bench → τ²-bench**：工具 + 用户模拟 + 策略遵守，客服/业务 Agent 必看
- **Agents' Last Exam / AutomationBench**：真实软件里的专业知识工作
- 读 2026 榜单五问：任务集版本？harness？effort？防护是否开启？成本？

## 核心机制：为什么旧读法失效

### 1. 长时程把方差放大

设单步成功率为 $$p$$，独立近似下 $$T$$ 步任务成功率：

$$
P(\text{success}) \approx p^{T}
$$

$$p=0.98$$、$$T=50$$ 时只剩约 36%。这解释了为何「单元测试全过」的模型在多小时任务上仍会崩——**错误恢复与状态管理**成为一等公民（见 [错误恢复与重试](../07-planning/error-recovery-retry.md)）。

### 2. Cost–Accuracy 曲线取代单点

2026 厂商报告常见形式：

$$
(\text{score}(e),\; \text{cost}(e)),\quad e\in\{\text{low},\text{med},\text{high},\ldots\}
$$

选型应最大化业务效用，而不是最大分：

$$
e^{*}=\arg\max_{e}\; U\big(\text{score}(e),\; \text{cost}(e),\; \text{latency}(e)\big)
$$

### 3. 防护干预 = 分数的一部分

生产防护开启后，网安/生物等双用任务可能被拒绝或改道。评测配置（防护关）与用户真实体验（防护开）可以差出两位数百分点——**榜单必须标注**。

### 4. 长时程任务要拆成「可判分的阶段」

小时级任务如果只有一个终态判分，失败时你只知道「没过」，不知道从哪一步开始崩。2026 可用的做法是给任务写**里程碑断言**，判分器逐步打分：

$$
\text{score} = \sum_{i=1}^{m} w_i \cdot \mathbb{1}[\text{check}_i] \Big/ \sum_{i=1}^{m} w_i
$$

$$\text{check}_i$$ 必须是**可执行**的（读文件、跑测试、查数据库、比对截图哈希），不能是「看起来对」。

```yaml
# 内测任务定义（示意）
id: nightly-pr-triage-01
horizon: long          # 预估 25–60 步
budget: { steps: 80, visual_tokens: 300000, wall_clock: 900 }
sandbox: docker+net-allowlist
milestones:
  - { id: list_open_prs, weight: 1, check: "pytest tests/eval.py::test_listed" }
  - { id: correct_triage, weight: 3, check: "diff <(jq .tags out.json) expected/tags.json" }
  - { id: draft_pushed, weight: 2, check: "git ls-remote origin refs/drafts/* | grep -q pr-952" }
guardrail_probe:       # 反向测试：不该做的事
  - { check: "! grep -r 'rm -rf' agent.log" }
```

### 5. 归因纪律：换一样，才敢说一样

| 想证明 | 必须固定 | 常见污染 |
|---|---|---|
| 模型变强了 | harness、工具集、防护模式、随机种子策略 | 顺手升级了 harness 版本 |
| 提示/工具改好了 | 模型与 effort | 同时换了模型 |
| 长时程真的稳 | 任务集版本与判分器 | 判分器跟着代码一起改 |
| 性价比更优 | 同一 effort 档 | 只报最高分不报成本 |

重复次数也要写进规则：$$n=1$$ 的差值不构成结论，长时程任务至少 3–5 次取分布（中位数与最差值一起看）。

## 2026 应纳入视野的基准

| 基准 | 考什么 | 为何重要 |
|---|---|---|
| Terminal-Bench 4.0 | 长终端任务 | 前沿编码/运维硬指标 |
| OSWorld 2.0 | 桌面 GUI | computer use 主战场 |
| SWE-bench Verified / Pro | 仓库修复 | 工程可信基线 |
| DeepSWE | 更难软件工程 | 拉开前沿 |
| τ²-bench | 工具 + 模拟用户 + 策略 | 业务 Agent |
| Agents' Last Exam | 真实专业软件任务 | 知识工作 |

## 工程含义

1. **内测集对齐 2026 协议**：长时程 + 可执行判分 + 成本日志，而不是 10 条短 QA
2. **固定 harness 做 A/B**：换模型不换 harness，才能归因
3. **记录防护模式**：研发榜与生产榜分开

## 常见误区

1. **拿 partial 分当「可托付率」**——过程分高不等于 strict 通过，托付决策要看 strict
2. **判分器写成人眼检查**——评测集自己就成了最大方差来源，必须落成可执行 check
3. **只看均值**——长时程要看中位数、最差值与「首崩步号」分布，均值会被少数惊艳 run 拉高
4. **一年前的榜单分数与今天比**——任务集换版本后不可比，只能同版本内比
5. **内测试题过少**——20 题以内的集子，一道题换版就能翻 5 个百分点

## 小练习

给你的产品挑 3 个真实「超过 30 步」的任务，各写出 3–5 个可执行里程碑 check 与一条 guardrail 反向 check，并估算 $$p$$ 与 $$T$$ 让你预期通过率——如果算出来低于 10%，说明这个任务现在根本不该自动化。
