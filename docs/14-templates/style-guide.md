# 风格指南

{% hint style="info" %}
**一句话**：这本手册的写作契约——原理要能推导、结论要有出处、图片要能解释信息；emoji 是调味品，不是主菜。
{% endhint %}

## 为什么有这版指南

初版全书由单一模板批量生成，出现了四个系统性问题，本版逐条纠正。写新页面或改旧页面前，先读这一节：

| 问题 | 初版的表现 | 本版要求 |
|---|---|---|
| 模板单一化 | 144 篇里 114 篇有「相关知识点」、96 篇有「常见误区」，顺序完全一致 | 按**体裁**分型，不同体裁结构不同，见第三节 |
| 篇幅注水或过短 | 正文中文字数中位数 521，仅 2 篇 ≥800，无一篇达到自己定的 1500 字 | 按体裁设定**硬下限**，不达标不得标 `published`，见第八节 |
| emoji 泛滥 | 全书 3182 个 emoji，平均每篇 22 个、约每 2.6 行一个 | 硬预算：**每页标题最多 1 个**，正文 0 个，见第二节 |
| 泛泛而谈 | 全书 **0 个数学公式**；核心概念只给类比不给机制；28 处数字断言大多无出处 | 原理型必须给**机制与公式**；事实必须**可溯源**，见第四、五节 |

## 一、总原则

**先讲清楚，再讲漂亮。** 判断一段文字该不该留的标准是：删掉它，读者是否少懂了一点？如果不会，就删。

三条底线：

1. **可验证**：每个数字、每条 API 行为、每个性能结论，都要能点到一个一手来源（论文、官方文档、源码）。
2. **可复现**：涉及"怎么做"的内容，给**数据契约 + 分步演示**（请求/响应的真实字段、`{% stepper %}` 的逐步状态、`{% tabs %}` 的分支结局），而不是"可以使用 X 实现"。全书不放可执行代码，见第六节。
3. **不重复**：同一个案例、同一张图、同一句类比，不要在多篇里反复出现充数。

## 二、Emoji 规范（硬预算）

初版的教训是：**只要允许标题挂 emoji，就一定会泛滥**。因此本版收紧为：

| 位置 | 允许数量 | 说明 |
|---|---|---|
| 页面一级标题 `#` | 0–1 个 | 整个页面最多 1 个，也可以完全没有；优先不加 |
| 二级/三级标题 | **0 个** | 一律纯文字，便于搜索、锚点稳定、目录整洁 |
| 正文 | **0 个** | 表情不能替代论证 |
| 提示块 | 每页 ≤3 个 | 用 GitBook hint 块：导语 `style="info"`（一句话）、经验 `style="tip"`、风险 `style="warning"`/`"danger"` |

{% hint style="warning" %}
**注意**：GitBook 侧边栏由 `SUMMARY.md` 渲染。`SUMMARY.md` 的章节标题**可以**保留 1 个模块 emoji，但条目层级不要滥用。
{% endhint %}

反例（初版真实写法）：

```markdown
## 📌 先看结论
## 🧩 核心概念
## 🍜 生活类比
## ⚙️ 工作流程
## 💻 伪代码
## ⚠️ 常见误区
## 🧪 小练习
```

正例：

```markdown
## 先看结论
## 核心机制
## 一份真实的数据契约
## 常见误区
```

## 三、体裁分类：不要用一套结构套所有文章

初版最大的问题是"每篇都必须是一句话 + 图 + 类比 + 误区 + 练习"。但资源卡片和原理论文根本不是一种东西。写之前先选体裁：

### A. 原理型（`type: knowledge`，难度 ⭐️⭐️/⭐️⭐️⭐️）

讲"为什么"和"怎么算"。应包含：

1. 问题动机（没有它会怎样）
2. **核心机制**——给出公式、推导或形状契约，不能只给类比
3. 直觉解释（类比放在机制之后，用来巩固，不要用来替代）
4. 工程含义（这个原理对构建 Agent 意味着什么）
5. 出处（原始论文/官方文档）

### B. 概念型（`type: knowledge`，难度 ⭐️）

讲"是什么、和什么不同"。应包含：

1. 定义 + 边界（什么算、什么不算）
2. 与相邻概念的对比表
3. 一个具体场景的例子
4. 出处

### C. 实战型（`type: knowledge`，偏工程）

讲"怎么做"。应包含：

1. 适用场景与前置条件
2. **数据契约 + 分步演示**：真实字段名的请求/响应 JSON、`{% stepper %}` 逐步走一遍生命周期、`{% tabs %}` 摆出各分支的实际结局。**不贴可执行代码**（见第六节），字段名与取值形态要对得上真实接口，不能臆造
3. 常见故障与排查
4. 出处

### D. 资源卡片（`type: resource`）

收录一手资源。应包含属性表（链接、来源、许可、活跃度）和**具体**推荐理由（不要"生态最大""体验好"这类空话）。属性表的「链接」行给**入口**（官网/仓库/论文，尽量 2 个以上），底部「参考资料」给**依据**（论文编号、官方文档、部署指南）；有几个官方来源就写几个，不硬凑。

### E. 实验型（`type: lab`）

带读者把一个 Agent 真跑起来。应包含：

1. 这个实验证明什么（一句话），以及跑通后读者应该看见什么
2. **分步演示**：`{% stepper %}` 逐步走一遍，分支结局用 `{% tabs %}` 摆出来；正文**不贴可执行代码**（见第六节），脚本放在仓库 `labs/` 里
3. **真实运行记录**：脱机跑一遍贴出来的输出，且记录里的数字要和正文的断言对得上
4. 常见翻车与排查

> 体裁决定结构，**不要求**每篇都有"生活类比""常见误区""小练习"。这些小节按需出现，不是打卡项。

## 四、深度要求：原理必须有机制

这是本版最重要的新增规范。

- 涉及数学、算法、评分、采样、损失、注意力的页面，**必须给出核心公式**。用 KaTeX 语法：

  ```markdown
  行内：注意力权重为 $$\mathrm{softmax}(QK^\top/\sqrt{d_k})$$

  块级（`$$` 单独成段）：
  $$
  \mathrm{Attention}(Q,K,V)=\mathrm{softmax}\!\left(\frac{QK^\top}{\sqrt{d_k}}\right)V
  $$
  ```

{% hint style="warning" %}
**注意（务必遵守）**：**行内与块级都用 `$$`**。GitBook 只解析 `$$...$$`；写成单 `$...$` 会原样显示成 `$P(y\mid x)$` 这样的纯文本，严重影响阅读。（GitHub 恰好相反：行内认单 `$`、块级认 `$$`。）本书以 GitBook 发布为准，因此**统一使用 `$$`**——代价是 GitHub 上会把这些行内公式按块级显示，换来 GitBook 上正确渲染。
{% endhint %}

- 公式之后必须解释**每一项在做什么**，以及**为什么需要它**（例如：为什么除 $$\sqrt{d_k}$$——防止点积随维度增大而方差膨胀、softmax 饱和）。
- 允许在给出公式后补生活类比，但**不能只有类比没有公式**。
- 涉及工程行为的，给**真实字段名的数据契约**（请求/响应/配置的真实键名与取值形态），而不是臆造的 API；要说明调用顺序时用 `{% stepper %}`，说明分支结局时用 `{% tabs %}`。

## 五、引用与事实核查

初版有 28 处"论文数据：提升约 20%"这类断言，却没有一处给出可点的论文编号。本版规定：

1. 任何数字（准确率、成本、比例、star 数、延迟）都要紧跟来源链接，或指向本手册的资源卡片页。
2. 引用论文用 `[标题](arXiv 链接)` 或 `[作者, 年份]` 形式；**每篇原理型/概念型页面底部必须有「参考资料」小节**（可含论文、官方文档、源码），没有则视为未完成。
   - 小节统一叫「**参考资料**」且只放外部一手来源；站内跳转一律归到「**相关知识点**」，两者不混排（旧稿的「相关资源」已全部改名）。
   - 知识页的「参考资料」不少于 **3 条**外部一手来源，每条都要**实际访问过**：链接能打开，且标题与所引论文/文档对得上（arXiv 用 `export.arxiv.org/api/query?id_list=` 核对标题，别凭记忆写编号）。
   - 某个资源本身只有一两个官方入口（例如论文未开源），就在卡片里**写明原因**，不许为凑数挂二手转载。
3. 性能数字必须带**条件**（数据集、模型、harness），因为同一模型换 harness 成绩可能差很多。
4. 不要用"业界普遍认为""众所周知"来支撑结论。

{% hint style="warning" %}
**注意**：GitHub star 数是会变的。写具体数字时标注**观测日期**，例如"约 21.8 万 star（2026-09）"。
{% endhint %}

## 六、图片规范：形象、生动、且能解释信息

图片的目的是**降低理解成本**，不是装饰。优先级从高到低：

1. **能自己画就自己画**：结构图、流程图、时序图、状态机用 Mermaid（GitHub 与 GitBook 原生渲染，可版本管理）。这类图改起来方便，永远和正文同步。
2. **概念插图用自绘 SVG**：需要"形象生动"的直觉图（如 Agent 循环、RAG 检索、记忆分层、多智能体协作）放在 `docs/.gitbook/assets/`，用 SVG（矢量、体积小、缩放不糊）。**自绘 = 无版权风险**。
3. **真实截图/照片**：仅在必须展示真实界面时使用，必须确认许可并注明来源，同样放 `docs/.gitbook/assets/`。
4. **不要**使用来源不明的网图、带水印的图，或用装饰性 emoji 拼贴冒充配图。

数量：原理型 1–3 张（其中至少 1 张 Mermaid），概念型至少 1 张。**图要准，不要多。**

### 图注（硬性要求，2026-09-22 起）

GitBook **会剥掉内容图片的 alt 文本**，读者在页面上看不到它；Mermaid 块更没有 alt。所以每张图必须有一条**读者可见**的图注：图下方空一行写 `*《图：……》*`。

- 图注写「读这张图要带走的那句话」——点名图里的真实节点/边/数字，给出机制、判据或取舍，20–60 字。
- **不得**写成「……的流程图 / 示意图 / 架构图」这类换个图也能用的空话；同一章内两张图的图注不得同句式、同文案。
- 上面那条 `![alt](…)` 仍然要写，但它是给无障碍工具与仓库阅读者的，**不能当作图注的替代**。
- 例外：纯装饰的首屏横幅（如 `docs/README.md` 的 `banner-home.svg`）与 `14-templates/` 里的示例。

### Mermaid 的解释语（硬性要求，2026-09-22 起）

Mermaid 块不强制配图注，但**必须被实质文字解释**，二选一即可：图前一句说明「这张图在讲什么机制」，或图后一句说明「读完要带走什么」。全书现状（2026-09-22 逐块量测）：217 块中 171 块带 `*《图：……》*` 图注，40 块由图前实质引导语解释，6 块由图后正文解释，**0 块裸图**。

- **纯指针不合格**：「如下图所示」「见下图」「流程如下」这种换个图也成立的句子不算解释；量测脚本 `audit16f` 的 F1/F2/F3 三类分别对应「两侧都没话」「只有空指针」「后置正文不足 20 个实义字」，都记为缺陷。
- 反过来，图注也不能省成一句「如下图」——它和图注受同一条反空话约束（上一条的措辞要求同样适用）。

### Mermaid 章色配色（硬性要求）

全书 Mermaid 块统一带**章色主题指令**：每个 ```` ```mermaid ```` 块的第一行必须是 `%%{init: ...}%%`，取所在章节的主色，让读者扫一眼就知道自己在第几章。2026-09-20 起全书块已全量注入，新增图不得省略。**这一节本身就是判据的规范来源**：`tools/checks/check_mermaid_palette.py` 现场解析下面的色表、再下面那行掺白公式和 `primaryTextColor` 的字面值去量全书 217 块（第 85 轮首跑读数 `blocks=217 chapters=21 contrast-pairs=868`，八桶全 0），改这张表等于改判据，删掉这一节判据会报「尺子断了」而不是「全书合格」——所以别拿它当注释维护。除配色外还有一条**可读性底线**：标签色与它所在底板（节点底色、actor 底色、note 底色）的 WCAG 对比度必须 ≥ 4.5:1，第 85 轮首趟就是被这条抓到一页把文字变量设成本章最浅那级掺白，量出 4 组 1.00–1.19:1 的白底白字。

### 排布与可读性（同样硬性）

**前提：量测引擎必须与线上同版本。** GitBook 用 `mermaid@11.14.0` 渲染，本地量测脚本也必须装同一个版本。第 15 轮就是栽在这里——量测端用了 12.0.0，而两个版本对「`flowchart` 方向 × 不相连 subgraph」的排布规则正好相反，一整轮的几何结论作废。校准办法：本地量出的自然尺寸要和线上 SVG 的 `viewBox` 对得上（实测 498×1543 对线上 497.5×1542.7）。

GitBook 会把 Mermaid 的 SVG 缩到正文列宽（约 1120px）：图越宽，字越小。量的是每块的自然宽 W 与自然高 H：`W > 1120` 判超宽，`W < 420 且 H > 380` 判细条。2026-09-22 在 11.14 下全库 180 块实测出的规律：

1. **宽度由「排数 × 每排节点数」决定，标签措辞几乎不影响**。同一条 5 排链，把长标签拆成两三行 `<br/>` 只降 5% 左右（1244→1174）；**无损合并掉一排**直接降 160px（1158→999）。要变窄就合并节点，别改文案。
2. **`flowchart TB` + 两个互不相连的 subgraph = 横向并排、内部也横向流**（实测 1098×244）；同一份源码改写成 `flowchart LR` 会塌成 349×840 的细条。所以「A vs B」并列对照图写 `TB`，并且两个 subgraph 之间不要留边。
3. **父图为 TB 时，后声明的 subgraph 渲染在左边**——源码顺序与读序相反，改完必须截图复核，图注里写的「左/右」也要跟着复核。
4. **一条长流程要拆成两块 mermaid**，而不是塞进一张：只要留一条跨排边，dagre 就把两排横向拼接（5+5 排一拼就 1600px 以上）。被删掉的那条跨阶段边必须写进两块图各自的图注，信息不得丢。
5. **节点必须带标签**。`A1 --> A2` 这种裸 id 会渲染成写着「A1」的空盒（第 15 轮在 [Graph of Thoughts](../04-prompt-reasoning/graph-of-thoughts.md) 修掉一处）；更隐蔽的是悬空引用——只在边上出现的 id 会凭空多出一个节点（[Reflexion](../04-prompt-reasoning/reflexion.md) 里曾有 `B2 --> C`）。
6. **细条不等于看不清**：W < 420 的竖排链文字仍是 16px，代价只是正文右侧留白。全库现存 9 张这类竖排图（时间线、单链流程），属可接受的版式取舍，不算可读性缺陷。**2026-09-22 操作者定调：这类图保留竖排，后续体检不再把「纵向语义图」计入待修**——判定方法是看语义而非看比例：时间轴、防御纵深、层级收敛三类允许竖排，普通并列/对照流程仍要按第 2 条改成横向双栏。

另外：rank 数不等于最长路径——旁支与孤立节点各占一排，别按「最长路径 ≤5」批量翻转方向（曾这样批量改 16 张，15 张超宽后回退）。判断一张图合不合格，要截**线上页面**的图看，本地能渲染不等于线上能看清。

配色公式固定：`primaryColor` = 主色掺白 90%、`secondaryColor` = 掺白 78%、`lineColor` = 掺白 45%、`primaryTextColor` = `#1F2937`。示例（02 章，写成一行）：

### 不放可执行代码（硬性要求，2026-09-22 起）

全书 **0 个可执行语言围栏**（python / js / ts / bash / sql / cypher…一律不许）。理由是读者的实际用法：AI 时代读者不会照着脚本跑，而一段跑不起来或已过时的代码比没有代码更伤信任。替代品按用途分三类：

| 要表达的东西 | 用什么 | 语言标记 |
|---|---|---|
| 接口/配置的字段与取值 | 数据契约 | `json` / `yaml`（必须真能解析，注释要写成读者可见的正文） |
| 张量、报文、路径的形状 | 形状契约 | `json`（值写成字符串，如 `"[n_seq, n_seq]"`） |
| 过程的先后顺序 | 可交互分步 | `{% stepper %}` + `{% step %}` |
| 同一入口的多种结局 | 可交互分支 | `{% tabs %}` + `{% tab title="…" %}` |
| 结构与流向 | 图 | `mermaid`（章色）、自绘 SVG |

两条配套纪律：**契约里的字段名要对得上真实接口**，宁可少写一个字段也不要臆造；**删代码不等于删内容**——原来靠代码承担的信息（顺序、分支、数量级、失败条件）必须用上面四类补齐，第 54 轮据此把 55 页 / 60 块 / 1502 行代码清零，同时正文净增 11.7 万字。

### 需要「会动」的图：用 SVG（SMIL）

流程/时序/对比类图示，可写成自带动画的 SVG（读者一眼就能看出「谁在等谁」），同样放 `docs/.gitbook/assets/`：

- **格式**：手写或从 Excalidraw/Figma 导出后用编辑器补 SMIL 标签；用 `<animate>`、`<animateTransform>`、`<animateMotion>`，`repeatCount="indefinite"`
- **为什么用 SMIL 而不是 CSS/GIF**：SVG 以 `<img>` 方式引用时，CSS 与 SMIL 动画仍会播放（脚本被禁用）；GIF 体积大且不清晰
- **可维护性**：纯矢量、可用文本 diff；改一个 `dur` 就能调速
- **深浅色适配**：自己画背景（如 `<rect fill="#f8fafc">`）与文字色，不要依赖页面背景；`viewBox` 固定
- **必须带 `role="img"` + `aria-label`**，并在正文补一段文字结论——动画只是辅助，静态阅读也要能懂
- **别滥用**：一篇最多 1 张动图，动画时长 3–6 秒一轮，只让「正在发生的事」动，静态结构不要闪

参考实现：`docs/.gitbook/assets/16-continuous-batching.svg`、`16-prefix-cache.svg`、`17-action-chunking.svg`。

{% hint style="warning" %}
**注意**：GitBook 云端会清洗 markdown 里的内联 `<svg>`/`<animate>`，因此**不要把动画写在 md 里**；用 `![](../.gitbook/assets/xxx.svg)` 引用独立文件，才能保留动画。
{% endhint %}

## 七、案例配给：防止单一项目刷屏

初版把 DeepSeek Harness / Pi / Claude Code 三个案例塞进了大量页面，`DeepSeek Harness` 出现在 **71/144** 个文件里，很多页面（如"向量数据库"）本身和它关系很弱，属于模板凑数。本版规定：

1. 案例必须**与页面主题直接相关**。写向量库就讲 FAISS/Qdrant/pgvector，不要为了填「源码案例」小节硬塞一个 harness。
2. 一个项目在全书出现次数应与其重要性匹配；**尽量避免同一个项目出现在超过约 10 个页面**，除非它在该主题上确为权威来源。
3. 引入项目案例时给出**为什么是它**，而不是只列名字。

## 八、篇幅与"发布"门槛

初版 `status: published` 被滥用：38 篇正文不足 300 字却标为已发布。本版规定：

| 体裁 | 正文中文字数下限 | 说明 |
|---|---|---|
| 原理型（`type: knowledge`） | 1200 | 含公式与推导 |
| 概念型（`type: knowledge`） | 600 | |
| 实战型（`type: knowledge`） | 900 | 含数据契约与分步演示 |
| 资源卡片（`type: resource`） | 150 | 但推荐理由必须具体 |
| 实验型（`type: lab`） | 1200 | 与原理型同档：一步跑得通的实验，正文要装得下动机、分步与真实记录 |
| 索引/导航页（`type: index`） | 不限 | |

**不达标不得标 `published`**，用 `status: draft` 或 `reviewing`。宁可少发，不要注水。

### 这张表就是判据的规范来源（硬性要求，2026-09-25 起）

每一行的体裁名后面**必须**带一个 `` `type: 键` ``——判据 `tools/checks/check_genre_floors.py` 只认这一处绑定，它按行读这张表来决定「哪一页该有多少字」。没有绑定的行等于没有这条规矩：判据会报「尺子断了」（读不到绑定就退出码 2），不会读成「全书合格」。字数口径是**正文里的中文字符数**，围栏块整块剔除（一屏贴来的 JSON 不算论证，否则贴图就能凑字数）；`draft`/`reviewing` 是本节自己给的合规出口，不受这条管。

一处如实的余地：`knowledge` 一个键同时套着原理/概念/实战三档，而 frontmatter 里没有字段能分开它们，所以判据按最低那档（**600 字**）硬判，另把「过了 600 但没到 1200」的页数打出来（`不可判(同键高档)=…`）。要把那一档也变成判据，得先决定加不加一个子体裁键——那是版式与元数据的决定，不是判据能替规范发明的规则。**而且那一档落地时上面「围栏剔除」的口径要重新量**：按 600 判，196 页里没有一页的判决会因「围栏算不算」而翻转；按 1200 判，有 **12 页**从合格变成不合格（正文 1138～1195、把围栏算进来则 1204～1307）。今天的口径不承重，那一天它就承重。

### `updated` 的口径（硬性要求，2026-09-22 起）

`updated` = **这一页正文最后一次发生读者可见变化的日期**：改字、改图、改图注、改表格都算；只动仓库里的脚本或 CI 不算。它不是首次发布日，也不是"我顺手存盘的日期"。

改内容时必须同步这一行——批量改动最容易漏的就是它。2026-09-22 一次量测发现 **79 页**的 `updated` 早于该文件最后一次提交日期：当天有十一次提交（补图注、核查引用、重排图形、增厚薄页）改过这些页，`updated` 却全部留在 09-20/09-21。

一个诚实的前提：GitBook 页面右上角那行「Last updated」用的是**平台自己的修订时间**，仓库里写什么都不影响它（已验证：某页 `updated` 写 09-20，线上显示 09-22）。所以修 `updated` 不是为了骗过读者，而是为了让仓库这份元数据能当真——维护者靠它判断"哪一页多久没动过了"，失真就等于给维护者假信号。

## 十、常见反模式（明确禁止）

1. ❌ **emoji 当标题装饰**：`## 🧩 核心概念` → `## 核心概念`
2. ❌ **只有类比没有机制**：解释注意力只写"像大脑在关注"，不写计算公式
3. ❌ **无出处的数字**："论文显示提升 20%"（哪篇？什么任务？）
4. ❌ **万能案例**：每个主题都拿同一个项目举例
5. ❌ **臆造接口**：`llm.think(goal)` 这种真实 SDK 里不存在的签名，无论是标成"代码示例"还是"伪代码"都不要写；换成一份字段名属实的 JSON 契约
6. ❌ **占位内容发布**：用空壳小节凑数还标 `published`
7. ❌ **机械打卡小节**：每篇都硬写"常见误区""小练习"，哪怕没有真内容
